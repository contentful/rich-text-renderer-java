● Critical
#01
Debug logging statements left in production code
android/…/views/TableRenderer.java Lines 79, 83, 85, 88, 101, 123, 126, 129 Information Leakage · Performance

Multiple System.out.println calls are present in production code. This exposes internal data structures and rendering state in device logs (Logcat), which can be read by other apps on non-SELinux-enforced devices. It also degrades performance on every render pass.

Recommended Fix

Remove all System.out.println calls. Replace any intentional diagnostics with Android's Log class gated behind a BuildConfig.DEBUG guard, or use a proper logging facade such as Timber.

#02
Blocking network call on the main (UI) thread — ANR risk
android/…/chars/EmbeddedLinkRenderer.java Lines 61–97 ANR · Concurrency

A CountDownLatch.await() call blocks the calling thread while an image is downloaded from the network. When invoked from the UI thread this triggers an Application Not Responding (ANR) dialog, which Google Play detects and penalises in store ranking.

Recommended Fix

Offload the download to a background thread (e.g. ExecutorService or Kotlin coroutines). Update the ImageSpan asynchronously using a handler post back to the main thread, or use an existing image-loading library (Glide / Coil) that handles this correctly.

#03
Swallowed exception hides production failures
android/…/chars/EmbeddedLinkRenderer.java Line 96 Error Handling

The catch block calls e.printStackTrace() and continues silently. Network failures, malformed image data, or interrupted threads are invisible to callers and monitoring systems, making production incidents impossible to diagnose.

Recommended Fix

Re-throw as a domain-specific unchecked exception, or propagate the error through the renderer's result type. At minimum, log via a structured logger that integrates with crash-reporting tooling (e.g. Firebase Crashlytics).

#04
Missing URL validation allows malicious URI schemes (XSS)
android/…/views/HyperLinkRenderer.java Line 120 Security · CWE-79

URLs sourced from Contentful rich text are passed directly to Uri.parse() and then to a WebView or Intent without scheme validation. An attacker who can publish or inject content can supply javascript:, file://, or intent:// URIs, enabling JavaScript execution inside the WebView or launching arbitrary intents.

Recommended Fix

Validate that the URI scheme is in an explicit allowlist (https, http, optionally mailto) before acting on it. Reject or sanitise everything else. Apply the same check in QuoteRenderer (#05) and TableRenderer (#06).

#05
Missing URL validation in QuoteRenderer — same XSS vector
android/…/views/QuoteRenderer.java Line 174 Security · CWE-79

Identical unvalidated URL handling as issue #04 is present in the quote block renderer, extending the attack surface to any hyperlink embedded within a blockquote.

Recommended Fix

Extract URL validation into a shared utility method and apply it in all renderers that process hyperlinks.

#06
Missing URL validation in TableRenderer — same XSS vector
android/…/views/TableRenderer.java Line 212 Security · CWE-79

Hyperlinks inside table cells share the same unvalidated URL-handling path, making every table with a hyperlink a potential XSS entry point.

Recommended Fix

Apply the centralised URL allowlist validator described in #04.

#07
Malformed HTML output — missing spaces between attributes
html/…/renderer/TagWithArgumentsRenderer.java Lines 50–56 Incorrect Output · HTML

The stringifyArgumentMap() method concatenates attribute key-value pairs without separating spaces, producing invalid HTML such as href="url"class="value". Browsers may fail to parse these attributes, breaking links and styles in the HTML renderer.

Recommended Fix

Insert a space character between each attribute pair during string construction: " " + key + "=\"" + value + "\"".

#08
Redundant if-else with identical branches — incomplete refactoring
html/…/renderer/TagRenderer.java Lines 104–109 Logic Error · Dead Code

Both branches of an if (tag.equals("a")) block return the identical string "</" + tag + ">". The condition has no effect and strongly suggests an incomplete or accidentally reverted refactoring that may have introduced a regression.

Recommended Fix

Review the original intent of the branch. If the <a> tag requires special closing logic, implement it; otherwise remove the dead conditional.

#09
NullPointerException — unguarded use of @Nullable path
android/…/views/TextRenderer.java Lines 95–103 NullPointerException

context.getPath() is annotated @Nullable but its return value is iterated directly without a null guard. Any code path that produces a null path will crash the renderer.

Recommended Fix

Add an explicit null check before iteration, or change the contract so getPath() returns an empty list instead of null.

#10
Unchecked cast — ClassCastException in table cell rendering
android/…/views/TableRenderer.java Line 120 ClassCastException

A node is cast to CDARichBlock without a prior instanceof check. Malformed or unexpected content from Contentful will throw a ClassCastException and crash the renderer entirely.

Recommended Fix

Guard the cast with if (cellNode instanceof CDARichBlock) and handle the else case gracefully (skip or log).

#11
Multiple unguarded casts and null dereferences in TableRenderer
android/…/views/TableRenderer.java Lines 145–160 NullPointerException · ClassCastException

After an instanceof check for CDARichTableHeaderCell, subsequent code paths do not account for the null case of cellNode, leading to cascading NPEs on unexpected data.

Recommended Fix

Introduce null guards and exhaustive type checks around all cell node accesses.

#12
ArrayIndexOutOfBoundsException in list decorator lookup
android/…/chars/ListRenderer.java Lines 91–100 ArrayIndexOutOfBoundsException

decorators.get(currentPosition) is called where currentPosition may exceed the list size after a modulo operation, particularly when the decorator list is empty.

Recommended Fix

Add a bounds check before access: ensure decorators is non-empty and use currentPosition % decorators.size() only when size > 0.

#13
NullPointerException — missing decorator null check in views ListRenderer
android/…/views/ListRenderer.java Line 76 NullPointerException

decoratorBySymbolMap.get(list.getDecoration()) returns null when the decoration type is not registered, but the result is used immediately without a null check, crashing any list with an unrecognised decoration.

Recommended Fix

Check for null before use and either apply a fallback decorator or log a warning and skip rendering.

#14
IndexOutOfBoundsException — unguarded first-element access
core/…/simple/RemoveEmpties.java Lines 54–55 IndexOutOfBoundsException

block.getContent().get(0) is called without first verifying the list is non-empty. An empty block from the API will throw at runtime.

Recommended Fix

Add a !block.getContent().isEmpty() guard before accessing the first element.

#15
Inefficient mark-checking logic — all conditions evaluated unconditionally
html/…/renderer/TextRenderer.java Lines 30–52 Performance

Sequential if statements (not if-else) evaluate every mark condition on every text node even after a match is found, wasting CPU cycles proportional to the number of marks.

Recommended Fix

Convert to if-else if chains or a Map<String, Supplier> lookup to short-circuit evaluation on first match.

#16
Misleading @Nullable annotation on always-initialised field
android/…/AndroidContext.javaLine 88API Contract

getPath() is annotated @Nullable but the backing field is always initialised to new ArrayList<>(). This forces callers to add unnecessary null guards while lulling authors of new code into a false sense of safety.

Recommended Fix

Change the annotation to @NonNull or remove it, and update the Javadoc to reflect the contract.

#17
Complex lastTextView logic — high risk of silent rendering bugs
android/…/views/BlockRenderer.javaLines 50–70Logic Complexity

State is carried across loop iterations via lastTextView with unclear semantics for when to append versus add a new view. This pattern has produced rendering omissions in similar codebases and is difficult to test in isolation.

Recommended Fix

Refactor to a stateless approach: build each child view independently, then compose them. Add unit tests that assert every content node produces visible output.

#18
Duplicated hyperlink-handling logic in HtmlRendererProvider
html/…/HtmlRendererProvider.javaLines 57–68Code Duplication

Identical logic is written twice to handle String and Map data types for hyperlinks. A future bug fix applied to one copy will be missed in the other.

Recommended Fix

Extract the shared logic into a private helper method and call it from both branches.

#19
Unchecked cast in core Processor — ClassCastException risk
core/…/core/Processor.javaLines 75, 92ClassCastException

Nodes are cast to CDARichBlock without an instanceof pre-check in the core rendering loop. Non-block node types from the Contentful SDK will crash the entire render pipeline.

Recommended Fix

Add instanceof guards before each cast in the processing loop.

#20
Missing null element checks on hyperlink children
android/…/views/HyperLinkRenderer.javaLines 62–73NullPointerException

The list returned by hyperlink.getContent() is checked for emptiness but individual elements are not checked for null before use, which the Contentful SDK does not guarantee.

Recommended Fix

Filter null elements from the content list before processing.

#21
IndexOutOfBoundsException in chars BlockRenderer

block.getContent().get(0) is called without verifying the list is non-empty, mirroring the same defect found in the core module (#14).

#22
TableRenderer exceeds 400 lines — violates Single Responsibility
android/…/views/TableRenderer.javaLines 1–350+Maintainability

The file handles layout creation, cell type detection, content rendering, and hyperlink processing in a single class. This makes it impossible to unit-test individual behaviours and extremely risky to modify.

Recommended Fix

Split into focused classes: TableLayoutBuilder, TableCellRenderer, and TableHyperlinkHandler.

#23
Potential off-by-one / NPE in TagRenderer path navigation
html/…/renderer/TagRenderer.javaLine 90IndexOutOfBoundsException · NPE

context.getPath().get(currentIndex - 1) will throw if currentIndex is 0 (negative index) or if getPath() returns null.

Recommended Fix

Guard with currentIndex > 0 && context.getPath() != null before the access.

#24
Default Decorator methods return empty strings — silent blank output
android/…/listdecorator/Decorator.javaLines 1–11API Design

The base Decorator class silently returns empty strings from getSymbol() and decorate() if a subclass forgets to override. This produces blank list bullets with no error.

Recommended Fix

Make the class abstract with abstract methods, so the compiler enforces implementation in every subclass.

#25
Repeated instanceof data-type checks across multiple renderers
android/…/chars/HyperLinkRenderer.javaLines 45–46Code Duplication

The pattern data instanceof String || (data instanceof Map && …) is duplicated in several renderers. Divergence between copies will cause inconsistent behaviour.

Recommended Fix

Extract into a shared utility method or a typed data class.

#26
Hardcoded dimension values — accessibility and density concerns
android/…/views/TableRenderer.javaLines 52–101Accessibility

Dimensions such as 32dp and 16dp are hardcoded in Java rather than defined in dimension resources, preventing scaling for accessibility font sizes and making design system changes require code edits.

Recommended Fix

Move all dimensions to res/values/dimens.xml and reference them via R.dimen.

#27
Mutable path list directly exposed via getPath()
html/…/HtmlContext.javaLine 28Encapsulation · Thread Safety

The internal path list is returned directly, allowing callers to mutate the context's state externally. This breaks encapsulation and is unsafe in any multi-threaded scenario.

Recommended Fix

Return Collections.unmodifiableList(path) or expose only specific add/remove methods.

#28
Inconsistent Java target version across modules
core/build.gradle · html/build.gradle · android/build.gradle—Build Configuration

Not all modules declare the same sourceCompatibility / targetCompatibility explicitly, creating a risk that different modules compile to different bytecode levels, which can cause UnsupportedClassVersionError at runtime on older Android API levels.

Recommended Fix

Define a single Java version in the root build.gradle as a shared variable and apply it consistently in every sub-module.

#29
Inefficient string concatenation in NumbersDecorator
android/…/listdecorator/NumbersDecorator.javaLine 12Performance (Minor)

position + ". " creates intermediate String objects on every list item render. Negligible for short lists but accumulates in deeply nested or very long lists.

Recommended Fix

Use String.valueOf(position).concat(". ") or a StringBuilder.

#30
Missing test coverage for table, embedded, and error-path scenarios
android/src/test/ · core/src/test/—Test Coverage

Test suites cover headings, marks, lists, and quotes, but there are no tests for table rendering, embedded image error paths, or malformed/null content inputs — the exact scenarios where most of the critical issues above manifest.

Recommended Fix

Add unit tests for: empty table cells, tables with hyperlinks, embedded images with network failures, and nodes with null content lists.
